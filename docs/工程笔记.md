## 1. 机器人启动（文档）

文档 `installation_robot_deployment/index.html` 的启动顺序：

1. 开机后，在“网络选择”界面连接 WiFi。
2. 在 Network 界面查看机器人 IP 地址。
3. 这个 IP 用于：
   - SDK 部署到机器人时输入；
   - 从外部 SSH 登录机器人在机器人上运行程序；
   - `galbot_sdk check-version --robot-ip <IP>` 做 SDK 与机器人系统版本兼容性检查。

文档把“程序运行在机器人 Orin 上”称为机器人端部署，适合生产环境和实时性要求高的应用。

文档只写到“网络选择”和“Network 界面查看 IP”；上电、自检、服务就绪的完整启动顺序在现有 refs 中没有找到，待现场确认。

### 启动前安全检查（文档）

- 确认机器人背部红色急停按钮已松开/已旋开（允许运动）。中文教程里的“打开状态”容易误解，英文原文是 `released`。
- Working ↔ Deployment 两个方向切换前都要先解除急停，否则平台会提示：
  `Cannot switch mode while emergency stop is active`。
- 做运动示例时，文档要求保持急停松开，并确保机器人周围有约 2 m 净空。
- 在 XCU 上执行 `/data/bin/sys_tool`，用 `q` 查看当前模式；正常应为 `WORKING_MODE`。模式为 `ABNORMAL` 时先排查，不要直接跑运动程序。

### 手臂规划需要的进程（文档）

手臂规划例程要求机器人上已经有这三个进程：

```text
/data/galbot/bin/service_motion_plan
/data/galbot/bin/robot_state_publish
/data/galbot/bin/eyehand_calib_publish
```

手臂、头、夹爪、升降本身不依赖导航；但如果当前工作模式默认开启了定位导航服务，仍需先建图，否则定位服务可能无法启动。新机器人首次使用前应先建图。导航前必须完成建图并定位。

2026-11-07 实测补充：本机 `service_motion_plan` 的 `get_localization_state = true`，组起始状态时会读 `/galbot/mes/global_pose`；定位异常期间即使只规划右臂，也会返回 `FAULT`（见 8.4–8.8）。所以“手臂不依赖导航”只适用于执行层，不能理解为规划服务不检查底盘定位；建图/定位是规划可用的前提之一。

### 环境变量（文档）

部署脚本实际只会向 `~/.bashrc` 追加 `PATH` 和 `PYTHONPATH`；`LD_LIBRARY_PATH` 不在脚本自动写入的范围内。如果 `import` 仍找不到 `.so`，再按文档的兜底配置手工补：

```bash

export PYTHONPATH=/data/galbot/lib:$PYTHONPATH
export PATH=/data/galbot/lib/galbot_sdk/bin:$PATH
```

改完后重新登录，或 `source ~/.bashrc`。注意非交互式 `ssh host "python ..."` 通常不会读 `~/.bashrc`；必要时用 `bash -lc` 或显式 export。

## 5. 上传并运行 Python（当前采用的方式）

文档给出的机器人端 Python 流程：

```bash
# 在 Windows / PC 上，把脚本传到 Orin
scp your_app.py galbot@<ROBOT_IP>:/userdata

# 登录机器人
ssh galbot@<ROBOT_IP>

# 进入脚本目录并运行
cd /userdata
python your_app.py
```

说明：

- 文档原文写的是 `python your_app.py`；如果机器人上没有 `python` 命令，可用 `python3 your_app.py`，但要先确认 `python3` 指向的是 SDK 支持的解释器。
- 文档的 Python 小节原文省略了 `cd /userdata`（C++ 小节有）；实际要先进目录，或用 `python /userdata/your_app.py`。
- 脚本放在 `/userdata` 是文档给出的机器人端部署路径；不要放到 `/data/galbot`、`/opt/galbot` 等系统目录。
- 控制通信走 embosa，不是 SSH。SSH 断开不一定代表控制断开；但程序生命周期仍应按 SDK 要求正常 shutdown。

### 最小生命周期冒烟脚本（依据文档）

先只验证 SDK 能否初始化、读取运行状态并正常退出，不做任何运动：

```python
import time

from galbot_sdk.g1 import GalbotRobot

robot = GalbotRobot()
if not robot.init():
    raise RuntimeError("robot.init() failed")

time.sleep(2)  # 等状态数据

print("is_running:", robot.is_running())

robot.request_shutdown()
robot.wait_for_shutdown()
robot.destroy()
```

文档要点：

- `GalbotRobot.init()` 只第一次生效。
- `destroy()` 之后同一进程不能再 `init`，需要重新开进程。
- 初始化后等约 2 秒再读状态，是示例里的做法。

## 6. embosa 网络配置（文档）

如果 PC 需要直接通过网口控制机器人，在 PC 的 SDK 目录执行：

```bash
./configure_embosa_ip.sh
```

交互要点（文档）：

- 机型选择 G-series。
- 输入 PC 的 IP。
- XCU 固定 `<XCU_IP>`，HPU 固定 `<ROBOT_IP>`。
- 脚本会配置 PC、XCU、HPU 三端，并重启相关 launcher。

### 重启后 IP 配置被改回去（文档）

如果机器人重启后 embosa IP 配置被重置，在 XCU 和 HPU 两端的 `/data/config/system.cfg` 中设置：

```text
enable_modify_embosa_cfg=false
```

然后重启 `launcher`。

### 有线连接异常的排查（文档）

如果“机器人上运行 SDK 程序可用，但有线连接不行”，先检查：

- PC、XCU、HPU 三端 IP 是否在同一网段；
- 两端的 `embosa_ip_config.json` 是否一致；
- PC 侧脚本写入的 PC IP 是否与实际网口地址一致。

SDK 出现 `get info failed` 或 `PUBLISH FAIL` 时，也先查这两个配置文件。

## 7. 版本、模式与快速排障（文档）

### 查看 SDK 与机器人系统版本

```bash
galbot_sdk check-version [--robot-ip <IP>]
```

如果命令不可用，登录机器人后查看：

```bash
cat /data/config/system.cfg
```

其中的 `CUR_VERSION` 字段是机器人系统版本。

### 进入 XCU 检查工作模式

文档给出的地址和账号：

```bash
ssh root@<XCU_IP>      # 密码：<XCU_PASSWORD>
cd /data/bin
./sys_tool
```

`sys_tool` 内：

- `v`：查看版本；
- `q`：查看当前模式；
- 正常应为 `WORKING_MODE`，`ABNORMAL` 需要先排查。

### 常见检查顺序（文档）

1. 急停按钮是否已松开。
2. XCU 的 `sys_tool` 模式是否正常。
3. 手臂规划所需的三个进程是否存在。
4. 查看日志和服务状态，例如 `singorix`、`galbot_chassis_service`。
5. 检查版本兼容性：SDK 1.10.0 对应的机器人环境为 V1.18。
6. 有线连接问题再查三端 IP 和 `embosa_ip_config.json`。

### 8.1 开发前建议核对（只读命令）

ssh galbot@<ROBOT_IP> 'ls /data/galbot/lib | grep galbot_sdk'

# Orin 侧：Python 解释器

# Orin 侧：Python 依赖

# Orin 侧：手臂规划三进程
ssh galbot@<ROBOT_IP> 'ps -ef | grep -E "service_motion_plan|robot_state_publish|eyehand_calib_publish" | grep -v grep'

#### 俯身转轴（模型 + MuJoCo 验证）

- 俯身是绕 `base_link` 的 **+y 轴**（左右横向轴）转动；正角度 = 向前低头。`head_base_link` 的 pitch 就是 `atan2(R[0,2], R[2,2])`。
- 五个腿关节在 `base_link` 系里的转轴（MuJoCo `data.xaxis`）：
  - `leg_joint1`：`+y`
  - `leg_joint2`：`-y`
  - `leg_joint3`：`+y`
  - `leg_joint4`：`+z`（不参与俯身）
  - `leg_joint5`：`+x`（不参与俯身）
- 因此没有单独的“俯身关节”，躯干 pitch 由三个腿关节合成：`pitch = q1 - q2 + q3`。`leg_joint4/5` 负责骨盆的偏航/侧倾，控制器里保持为 `0`。
- `control_pitch` 的转动中心是腿部末端（骨盆，`leg_end_effector_mount_link`）：求解时保持腿部 EE 的 `x/z` 不变，只改变其姿态，所以看起来是躯干绕骨盆点转动，而不是绕某个关节或底盘转动。

### 8.3 XCU、HPU 与“base”的区别（文档 + 实测）

先纠正命名：官方文档里没有 “XPU”，只有 **HPU** 和 **XCU**；按上下文，之前说的 “xpu” 应指 XCU。

#### 不是同一层

| 名称 | 是什么 | 负责什么 | 依据 |
| --- | --- | --- | --- |
| HPU | 高性能计算单元，本机为 `Jetson AGX Orin Developer Kit` | 定位、导航、规划、感知、AI 推理；服务如 `localization`、`navigation`、`mps`、`perception` | 官方 troubleshooting 文档；SSH 登录 `<ROBOT_IP>` 实测型号 |
| XCU | 实时控制单元 | 底层电机、关节执行、末端执行器、整机模式管理；如 `singorix` 运动控制 | 官方 troubleshooting 文档；`<XCU_IP>` ping 通 |
| base | **不是算力单元，也不是文档里的整机模式** | 硬件上指底盘（Base/Chassis，含轮子和电源）；坐标上指 `base_link`/`base_footprint`/`base_pose`；`/userdata/user_config/base` 和 `apply_scene="base"` 只是本机配置里的名字，G1 文档没有把它们定义为模式或计算层；`sys_tool v` 的 baseline 是“版本基线”，也不是 base 模式 | 官方术语表、troubleshooting、SDK `ModeType` 枚举 |

SDK 1.10.0 的 `ModeType` 枚举里没有 `BASE_MODE`，整机模式只有 `WORKING`、`TELEOPERATION`、`DEPLOYMENT`、`SLEEPING`、`OTA`、`ABNORMAL`、`CHARGING`、`FACTORY`、`NAVIGATION`、`DATA_COLLECTION` 等。所以“切回 base”不是一次整机模式切换；它最多是底盘参数场景/配置文件的叫法，不能把它当成与 HPU/XCU 并列的一层。

`LegController` 能不能用，取决于：

1. SDK 与机器人通信正常（`discovery_server` + `service_hpu_comm`）；
2. XCU 的运动控制服务在运行（如 `singorix_wbcs_main`）；
3. 整机模式允许运动（`WORKING_MODE`，急停已松开）；
4. 手臂规划另需 HPU 上的 `service_motion_plan`、`robot_state_publish`、`eyehand_calib_publish`。

所以：**切到 base 本身不等于这些功能可用**。本次只读检查和 15° 腿部俯身能成功，是因为通信恢复，且腿部直接关节控制不依赖 `service_motion_plan`，不是因为“切到了 base”。

#### 快速定位

- 能连上但不动 / 动作异常 → 优先查 XCU。
- 能动但地图、路径、避障、感知结果异常 → 优先查 HPU。
- 整机模式用 XCU 的 `/data/bin/sys_tool` 查询（`q`）；模式切换需要松开急停。

以上是文档依据 + 本次只读检查。“base 场景是否已生效”没有在本次运行中单独验证，不能把配置文件里的 `apply_scene="base"` 当成运行中已生效；2026-11-06 就出现过配置文件写了 `WORKING_MODE`、运行中的 launcher 仍报 `DATA_COLLECTION_MODE` 的情况。
